## 3. Очерёдность
1. Search & Documents 2.0 — принят в 15 проверенных сценариях #286.
2. Plugin Update Engine — #290 принят в проверенных сценариях. Diagnostics Engine — #291 принят по общему отчёту пользователя. Следующий этап: SDK разработчика, затем AI Commander 3.0. Номера следующих CI не резервировать: фиксы могут сдвигать их.
3. **Archive Reliability 2.0 — следующий приоритет после текущих плагинов.** По сообщению пользователя, обновление изменённых начинается только после входа в список, а в комментариях бывает «Оригинал не получен» даже после синхронизации; интернет/VPN iPhone 8 включены. Причина пока неизвестна. Проверять по этапам Collector → Live Bridge → подтверждённый импорт SQLite → обновление UI, включая удалённые сообщения, повторные редакции и уже открытые обсуждения. Не восстанавливать выдуманные оригиналы. Не расширять сбор за пределы существующих разрешённых данных.
4. Не добавлять произвольные новые функции раньше этих этапов без согласования. Критические ошибки и CI исправлять своевременно.

## 5. Неизменные правила
- Сохранить существующую SQLite (без сброса/второй БД), Ghost и приватность, независимый Collector на iPhone 8 и Live Bridge; версии развёрнутых скриптов проверять перед изменением. Не публиковать ключи, сессии, приватные сообщения, персональные ID и сетевые секреты.
- Не расширять доступ к секретным, защищённым, одноразовым и исключённым данным. Раздельные разрешения плагинов, явное согласие на внешнюю передачу, ручная отправка сообщений.
- Точечные правки, тесты, проверка HEAD перед записью, подтверждение результата GitHub. Отдельно различать локальные тесты, успешный CI, проверку на iPhone.
- Не запускать сборки ради документации. Не обещать фоновые действия или успешный результат до проверки.

## 6. Обязательное постоянное обновление
**После каждого коммита кода, результата CI, подтверждённого теста пользователя, обнаруженной существенной ошибки или изменения плана обновляй START_HERE.md в ветке goldgram-project-docs.** Это постоянная запись между чатами, а не разовый промпт.
- Перезаписывать актуальную таблицу, следующий шаг, блокеры и очередь; удалять устаревшие строки, сохранять постоянные правила. Не превращать START_HERE в длинный журнал: ориентир до 100 строк.
- В том же документационном коммите обновлять CURRENT_STATUS (статус), DECISIONS_LOG (добавлять историю/доказательства), PROJECT_CONTEXT (только архитектурные изменения), roadmap и справочник API (только если затронуты).
- Проверять сохранение по HEAD ветки и содержимому/списку изменённых файлов; сообщать пользователю точный SHA документационного коммита. Если запись не удалась, явно сообщить об этом, не утверждать, что сохранено.
- При входе из нового чата не записывать фиктивный прогресс. Если GitHub изменился — синхронизировать факты. Если пользователь просит только консультацию, не создавать коммит без изменения состояния проекта.
